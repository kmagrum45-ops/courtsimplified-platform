# CourtSimplified — session findings (2026-09-11)

Context for a fresh chat: this covers two connected investigations in the
`courtsimplified` repo (Next.js/TypeScript, Windows, git on `main`). Written
to be self-contained — no prior conversation needed.

## PART 1 — The Ontario Annual Practice Book work is NOT in the site

**Question asked:** find every place the Annual Practice work exists and
whether it's used in the live product.

**Answer: it does not exist in the product. It was never imported.** What
exists is an empty container built to receive it, and that container is
never read by anything.

### The two files that were supposed to hold it

| Path | Reality |
|---|---|
| `src/lib/case-system/authority/ontarioCivilAuthorityCollection.ts` | **Deleted** in commit `41b4dbc` (2026-09-10) |
| `src/lib/case-system/authority-intelligence/authorityBrainBridge.ts` | **Never existed** — zero hits repo-wide |

The deleted file survives only in an abandoned, git-ignored agent worktree
(`.claude/worktrees/agent-add7509fa37610fac`, branch `4a8a42c`, locked,
excluded via `.git/info/exclude:11`, 0 tracked files). That is not the site.

The deletion was deliberate and well-documented. Commit `41b4dbc` recorded
independent re-verification: all three export names grepped repo-wide
(`ONTARIO_CIVIL_AUTHORITY_COLLECTION`, `getOntarioCivilAuthorityCollection`,
`getOntarioCivilAuthorities`), no real import anywhere, and `tsc --noEmit` +
`npm run build` both clean with the file gone. It was a **third duplicate**
registry of the same regulation, superseded by a better-sourced one.

### What Annual Practice material actually exists

Only in `src/lib/case-system/authority-intelligence/verifiedAuthoritySeedRegistry.ts`:

- 12 authority entries total
- **11 have `annualPracticeLinks: []`** (empty)
- **1 has a single placeholder** (line 338, Rule 20 Summary Judgment) whose
  own text reads:
  - `commentarySummary: "Annual Practice commentary should be added from verified user-provided extraction."`
  - `notes: ["Pending Annual Practice extraction."]`
- The registry's own `warnings` array says:
  `"Starter registry only. Add Annual Practice authorities only after verified extraction."`

That is a to-do note, not content.

### The field is write-only

`annualPracticeLinks` is declared in `authorityRegistryArchitecture.ts:179`
and set in the data — but grepping every *read* of that symbol across `src/`
and `app/` returns exactly one hit: its own type declaration.

**Nothing reads it.** Even if all 12 entries were populated tomorrow, no page,
route, component, warning, case field, or document gate would display them.

### Live code paths (both real, neither carries Annual Practice data)

```
Chain A: verifiedAuthoritySeedRegistry
      -> authorityRetrievalEngine
      -> courtSimplifiedBrain
      -> /api/assistant-chat, /api/case-summary, civil+family intake adapters

Chain B: betaProcedureAuthority
      -> /api/rules/procedures, /api/cases/form-applicability
      -> app/builder/page.tsx:1026 (ProcedureAuthorityDisplay), app/forms/page.tsx
```

Chain B is the real user-facing authority surface. `betaProcedureAuthority.ts`
contains **no Annual Practice material at all**.

### Provenance metadata

The general schema is decent — `verificationStatus` (26 uses), `lastVerified`
(19), `sourceUrl` (17), `verifiedAt` (8).

But **none of the Annual Practice–specific provenance fields exist**: no book
year, no edition, no extraction status, no source package. `annualPracticeLinks`
offers `rule`, `sectionLabel`, `commentarySummary`, `pageOrPinpoint`, `notes` —
and `pageOrPinpoint` is unused. There is no way to record *which year's book* a
passage came from, which matters because the Annual Practice is republished
annually.

### Plain English: where does this appear for a user today?

**Nowhere.** Not one page, warning, or generated document. If Annual Practice
work was done elsewhere, **none of its output reached this repo.**

### Licensing flag (important)

Annual Practice commentary is **copyrighted Thomson Reuters material**, not a
public source like e-Laws. It is not on the project's acceptable-source list
(CLAUDE.md section 2: ontario.ca, ontariocourts.ca, ontariocourtforms.on.ca,
CanLII, Justice Ontario, Law Society of Ontario). Bulk-extracting it into a
product raises a licensing question separate from whether the code works. The
registry's own "only after verified extraction" warning reads like someone
already had that concern.

**This is a licensing decision first and an engineering task second.**

## PART 2 — A data-loss trap found while investigating, now fixed

### What was wrong

`scripts/snapshot/createDeveloperSnapshot.mjs` — run by `npm run snapshot` —
opened with:

```js
fs.rmSync("_PROJECT_REGISTRY", { recursive: true, force: true })
```

It wiped the **entire** directory, then wrote back **8 flat files**. The
directory held **59**.

The other **52 files are not generated by that script and nothing in
`scripts/` can recreate them**:

- `PROJECT_DOCUMENTATION/` (31 files) — Ontario form routing queues, provenance
  reports, certification pipeline output, conference posture matrices.
  Substantive work, up to 294 KB per file.
- `GENERATED_DOCUMENTATION/` (21 files) — **named "generated" but produced by
  something else.** The script contains zero references to either directory
  name and writes only to `path.join(registryDir, name)` — flat, top level.

`_PROJECT_REGISTRY/` is **gitignored** (`.gitignore:156`) with **zero tracked
files**, so `git checkout` could not recover any of it.

**Running a normal-looking npm script would have silently destroyed ~1.9 MB of
unversioned work.**

Largest files that were at risk:

| Size | File |
|---|---|
| 708 KB | `GENERATED_DOCUMENTATION/ARCHITECTURE_MODEL.json` |
| 294 KB | `PROJECT_DOCUMENTATION/ONTARIO_FORM_CERTIFICATION_PIPELINE_REPORT.json` |
| 149 KB | `PROJECT_DOCUMENTATION/ONTARIO_COMPLETE_FORM_ROUTING_QUEUE.csv` |
| 135 KB | `GENERATED_DOCUMENTATION/WORKFLOW_INTEGRATION_MODEL.json` |

### The fix (commit `45534a0`)

`ensureCleanDir()` now deletes **by name** from a `GENERATED_FILES` constant
listing the 8 files the script actually owns, then ensures the directory
exists. Unknown files and all subdirectories survive — which is also what the
`Compress-Archive` step at the end of `main()` expects, since it zips the whole
tree rather than those 8 files.

### Verification (run for real, not reasoned about)

A full off-repo backup was taken first, to
`C:\Users\kmagr\courtsimplified-registry-backup\20260911-233918\` (52 files,
1.9 MB — still present).

| | Before | After |
|---|---|---|
| Total files | 59 | **62** |
| The 52 doc files | 52 | **52** — `diff -rq` = 0 differences, both dirs |
| Under the OLD code | — | would have been **7** |

All 8 generated files refreshed, so the script still does its job. Its embedded
`npm run build` is clean. `git status` showed only the one intended file changed.

## OPEN DECISIONS (nothing is blocked; these are judgment calls)

1. **Should `PROJECT_DOCUMENTATION/` go into git?** 31 files of substantive
   Ontario forms work, currently gitignored with zero version control behind
   it — the least-protected thing in the project. The fix removed one script
   that could destroy it; it did not make it safe. An accidental `rm`, a bad
   merge, or a disk failure still loses it. Tradeoff: roughly 600 KB of
   CSV/JSON added to git history.

2. **`GENERATED_DOCUMENTATION/` is misnamed and unreproducible.** Nothing in
   `scripts/` produces it; whatever created it is gone. Those 21 files
   (including the 708 KB `ARCHITECTURE_MODEL.json`) are one-offs, not
   regenerable artifacts. Worth either renaming the directory or finding/
   recording what made it.

3. **Annual Practice: licensing call before any engineering.** See the flag in
   Part 1. The container exists and is wired to nothing; populating it is the
   easy part, and the wrong part to start with.

4. **Stale references are cosmetic only.** Four files under
   `_PROJECT_REGISTRY/GENERATED_DOCUMENTATION/` still list the deleted
   `ontarioCivilAuthorityCollection.ts`. They are untracked, local-only, never
   ship, and cannot be regenerated. They caused one wrong turn (an AI reading
   them and hunting a deleted file) but carry no product risk. Trust `git log`
   and the live tree instead.
